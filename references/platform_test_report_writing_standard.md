# 平台打包与真机验证测试报告编写规范

本文沉淀平台固件打包、SDK 编译、真机验证类任务的报告输出规则。后续 3021/3122 或其他模组打包验证报告默认按本文结构生成。

## 核心原则

- 报告先给结论，再给过程。读者打开报告后应先看到当前测试是否通过、覆盖了多少、是否有遗留问题。
- 报告不是流水账，必须说明“为什么测、怎么测、测了多少、结果如何、问题怎么闭环”。
- 不能只写总数。关键配置包、专项功能、失败复测、SDK 编译产物运行态都要有量化数据和表格。
- 问题必须写到可定位：影响范围、现象、处理动作、最终归因。没有问题时不要硬凑问题列表，可写“未发现未闭环问题”。
- 报告中的结论只能来自证据文件：release summary、download summary、runtime summary、SDK build summary、serial log、截图、附件索引。

## 推荐生成流程

1. 先生成详细结果 Markdown：展开所有 release、配置向量、执行结果、复测动作、日志 marker 和证据路径。
2. 再生成结构化 HTML 报告：面向评审和邮件阅读，保留关键数字、关键表格和问题闭环。
3. HTML 发送前必须校验：UTF-8、标题、中文章节、表格字段、关键数字、证据链接路径。
4. 邮件正文只放摘要和附件说明；完整报告以 HTML + result.zip 附件交付。

## HTML 报告固定结构

### 标题

格式示例：`3021 模组全垂类 UI-only 打包、固件与 SDK 真机验证报告`。

标题下方必须紧跟“测试结论”，不能把结论放到最后。

### 测试结论

用 1-2 段简短说明当前结果：

- 覆盖范围：模组、垂类、产品、配置包、SDK 数量。
- 总体结果：UI 打包、下载、固件真机、SDK 编译、SDK app.bin 真机是否通过。
- 异常结论：是否有未闭环缺陷；边界包、控制变量包、纠偏包的最终归因。

示例口径：

```text
本轮覆盖 6 个垂类、21 个主配置固件、3 个连续学习纠偏固件和 6 个 SDK。
UI 打包、固件下载、SDK 下载、SDK 本地编译、SDK 编译产物烧录运行均通过；未发现需要研发介入的平台配置、固件产物或 SDK 产物缺陷。
```

### 1. 测试目的

说明发这份报告是为了验证哪些需求功能是否正常。至少包含：

- 平台 UI-only 打包链路是否可用。
- 固件产物是否能烧录并在设备上运行。
- 对应产品能力是否生效，例如基础唤醒识别、命令词、音量、协议、多唤醒、语音注册。
- SDK 是否能下载、按 readme 编译，并且编译出的 `app.bin` 能烧录运行。
- 历史失败或风险项是否闭环。

### 2. 测试方案

让读者知道“怎么测”。必须写功能和验证方法，而不是只写工具名。

建议表格字段：

| 功能模块 | 验证方式 | 通过判据 |
|---|---|---|
| UI 打包 | UI 新建产品、配置基础参数、导入算法模板、生成 release | release 状态 success，产物可下载 |
| 基础配置 | 默认/左边界/右边界向量覆盖 timeout、音量、波特率、保存开关 | 配置进入 web_config，设备表现匹配 |
| 协议链路 | 协议口发帧/收帧，日志检查 RX/TX | 协议可通信，动作或播报可观测 |
| 声卡识别 | 指定声卡播报唤醒词、命令词、音量词 | 日志出现 Wakeup/intent/pinyin |
| 多唤醒 | 指定切换、循环切换、协议切换分包验证 | 切换后候选唤醒词可识别 |
| 语音注册 | 指定学习、连续学习、关闭隔离；清配置后验证 | 出现成功 marker，学习语料生效 |
| SDK | 下载、解压、读 readme、build、烧录 app.bin | 编译和运行态 gate 均通过 |

方案中必须体现打包策略：

- 固定一个代表产品，同产品下多个 release。
- 用最小组合包覆盖最多等价类和依赖链路，不一参一包。
- 支持专项能力才打专项包，不支持则裁剪。
- 失败后用控制变量包或纠偏包闭环，不直接下结论。

### 3. 测试用例和结果

必须量化。建议至少包含三个表格。

#### 总体量化结果

| 测试项 | 验证内容 | 数量 | 执行结果 | 结论 |
|---|---|---:|---|---|
| UI-only 打包构建 | 主配置 + 纠偏 release | 24 | 24 通过 / 0 失败 | 通过 |
| 固件产物下载 | fw.bin、web_config、zip 有效性 | 24 | 24 通过 / 0 失败 | 通过 |
| 主固件真机运行态 | 启动、协议、声卡、专项能力 | 21 | 18 正向通过 / 3 边界闭环 | 通过 |
| SDK 编译 | readme + build.sh + app.bin | 6 | 6 通过 / 0 失败 | 通过 |
| SDK app.bin 真机 | 编译产物烧录和运行态 | 6 | 6 通过 / 0 失败 | 通过 |

#### 配置包结果

字段至少包含：

- 垂类
- 产品
- profile
- releaseId / 版本号
- 版本描述
- 关键配置向量：timeout、音量、baud、voice、多唤醒、模板
- 最终结论：通过 / 复测通过 / 边界闭环 / 失败 / 阻塞
- 说明：为什么这样判定

#### SDK 结果

字段至少包含：

- 垂类
- SDK 来源包
- readme 是否存在
- build 返回码
- app.bin size / sha256 前缀
- 烧录返回码
- 运行态返回码
- 结论

## 4. 测试问题与分析

有问题才展开，没有未闭环问题时可写一句：`本轮未发现未闭环的平台配置、固件产物或 SDK 产物缺陷。`

出现问题必须按以下字段写表格：

| 问题 | 影响范围 | 现象 | 处理动作 | 最终分析 |
|---|---|---|---|---|

要求：

- 影响范围必须写到包、垂类或配置项，不能只写“部分用例”。
- 现象必须写观察证据，例如日志 marker、返回码、截图、产物缺失。
- 处理动作必须写复测方式，例如清配置、重新上电、冒烟固件对照、控制变量包、纠偏包。
- 最终分析必须落到明确类型：平台问题、固件问题、SDK 问题、设备/线序问题、测试执行问题、边界行为。
- 不要使用泛化英文 `RISK`、`UNKNOWN` 作为主要结论；需要中文解释清楚。

## 证据文件要求

报告末尾必须列证据索引：

- 主计划 JSON：配置包矩阵和 coveragePoints。
- release poll summary：构建状态和 releaseId。
- download summary：固件/SDK 下载和结构校验。
- firmware runtime summary：每包烧录和运行态结果。
- failure rerun/control-variable summary：失败复测证据。
- sdk build summary：SDK 编译证据。
- sdk app runtime summary：编译产物真机证据。
- serial raw log / screenshots / result.zip：必要附件。

## 版式要求

- HTML 默认使用浅色科技感背景，不用纯黑背景，不用过白无层次背景。
- 首页必须有 3-5 个数字卡片，例如覆盖垂类、release 成功率、固件包数量、SDK 通过率。
- 表格是主体，不要用大段散文堆叙述。
- 关键异常项单独成表，不要混在总结果里一笔带过。
- 中文字段必须完整显示，生成后必须做 UTF-8 读取校验。

## 禁止项

- 禁止只写“全部通过”但没有覆盖范围和数量。
- 禁止只写 profile 名称，不展开该包覆盖哪些配置和功能。
- 禁止把左边界观察包写成正向功能失败或正向功能通过，必须说明边界语义和由哪个包覆盖正例。
- 禁止把重试后恢复吞掉首轮异常；首轮异常和复测结论都要写。
- 禁止把测试脚本缺陷、历史状态污染、台架瞬态问题写成平台或固件缺陷。
- 禁止报告中输出 token、内部账号敏感信息。
